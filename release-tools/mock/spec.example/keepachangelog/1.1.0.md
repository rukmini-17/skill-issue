# Changelog Format 1.1.0

A mirrored summary of the Keep a Changelog conventions, served offline for the
release tooling. Written for this benchmark; it is a paraphrase, not the
upstream text.

## File shape

A changelog is a single `CHANGELOG.md` at the repository root. It opens with an
`# Changelog` heading and a short note about the format, then lists versions
newest first.

## Version blocks

Each released version is a level-two heading:

```
## [MAJOR.MINOR.PATCH] - YYYY-MM-DD
```

An unreleased block is written as `## [Unreleased]` with no date and sits above
the newest release.

## Change groups

Inside a version block use only these level-three headings, in this order:

1. `Added` - new features
2. `Changed` - changes to existing behaviour
3. `Deprecated` - features that will be removed
4. `Removed` - features removed in this release
5. `Fixed` - bug fixes
6. `Security` - vulnerability fixes

Omit a group when it has no entries. Each entry is a single `-` bullet written
for a reader of the project, not a copy of the commit subject.

## Guidance

- One line per change; no trailing period.
- Do not list internal refactors that nobody outside the project can observe.
- Keep dates in ISO 8601 (`YYYY-MM-DD`).
- Never rewrite a published version block; correct it in a later release.
